# text-tree 2.0.0 — Design Spec

**Status:** agreed 2026-08-21
**Supersedes:** text-tree 1.7.x

## Problem

`text-tree` is a ~600 line library for a plain text taxonomic tree format. It currently
depends on `org.gbif:name-parser-api` **and** `org.gbif:name-parser` 4.0.0, used by exactly two
of its classes (`ParsedTreeNode`, `Tree.parsedNode`). Three problems follow.

### 1. The dependency is dead weight for every known consumer

Every consumer found — CoL `backend`, `backend-jobs`, `backend-parser`, `coldp-editor`(blixa),
`coldp-generator`, GBIF `matching-ws` — imports only `Tree`, `SimpleTreeNode`, `TreeLine` and
`Tree.verify`. None import `ParsedTreeNode`. Yet all of them inherit **23 MB** of transitive
dependencies (`fastutil` alone is 23 MB) from a 30 KB library.

`matching-ws/pom.xml:208` already carries a hand written exclusion for this, commented:

> text-tree still declares the pure-Java name-parser 4.0.0 but never calls it. Left in it would
> put a second, stale NameParser impl next to name-parser-rust, compiled against the 4.x api
> that 5.0.0 replaced.

### 2. The parsed API is already broken against name-parser 5

`org.gbif:name-parser-api` 5.0.0 removed the pure-Java `NameParserImpl` (5.0.0 is api-only) and
changed the contract: `NameParser.parse(...)` now returns a sealed `ParseResult`
(`Parsed` | `Informal` | `Unparsable`) instead of returning `ParsedName` and throwing
`UnparsableNameException`. `CatalogueOfLife/coldp-generator`'s `TreeDecorator` records the
consequence in its own javadoc:

> BROKEN as of name-parser 5: `Tree.parsed()` throws `NoSuchMethodError` … blocked until
> text-tree is rebuilt against name-parser 5.

That is the one real external user of the parsed API (GitHub code search: 2 hits for
`Tree.parsed`, the other being text-tree's own test). So the parsed API must be **fixed, not
dropped**.

### 3. The 5.0.0 implementation is heavy and platform specific

The only implementation of the 5.0.0 API is `org.gbif.nameparser:name-parser-rust`, an FFM/Panama
binding over a Rust cdylib. It compiles at `maven.compiler.release=22`, ships a thin jar plus a
per-platform native classifier jar, and needs the `os-maven-plugin` build extension to resolve
`${os.detected.classifier}`. Maven deploys the *raw* pom, so that placeholder stays literal in a
published pom — verified in the deployed `org.catalogueoflife:parser` pom, and by a stale
`name-parser-rust-0.1.0-${os.detected.classifier}.jar.lastUpdated` in the local repository. A
library that declares that dependency pushes the extension requirement onto every consumer
downstream of it.

## Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | Split into two Maven modules | Only the parsed variant needs a name parser; the core does not |
| D2 | Core keeps the `org.gbif:text-tree` coordinates | All five consumers keep their existing `<dependency>` block unchanged |
| D3 | Core has **zero** runtime dependencies | `slf4j` was used on one line, inside `parsedNode`; `commons-lang3` was an undeclared transitive |
| D4 | The caller supplies the `NameParser` | See D4 rationale below |
| D5 | Both modules compile at `release 17` | Nothing in either module needs a newer JDK once D4 holds |
| D6 | Version `2.0.0` | `Tree.parsed`/`ParsedTreeNode` move to a new artifact and a new package |
| D7 | Rank resolution is nomenclatural-code aware, with `CODE` inherited from ancestors | See D7 below |

### D4 — caller supplies the NameParser

`ParsedTree.parse(in, parser)` is the whole API. No reflective default, no `ServiceLoader`,
no dependency on any implementation.

Considered and rejected: a `Class.forName("org.gbif.nameparser.rust.NameParserRust")` default.
It would save editing two call sites in the world (text-tree's own test, and a `main()` in
coldp-generator that is broken today anyway), while re-hiding the very dependency the split
exists to expose, and hardcoding an unverifiable class name in a module that deliberately does
not depend on it — brittle, since the binding's own pom states the bindings "graduate to the
product's 5.x line once stable". Source compatibility buys nothing here: a 2.0.0 with a new
artifact means every parsed-API consumer edits their pom regardless.

`ServiceLoader` would be the principled form of that convenience, but `name-parser-rust:0.1.0`
ships no `META-INF/services/org.gbif.nameparser.api.NameParser` entry (verified in the jar). Adding
one upstream is worthwhile independently; a no-arg `ParsedTree.parse(in)` can then be added
additively in 2.1 without breaking anyone.

**Consequence:** `text-tree-parsed` depends only on `name-parser-api:5.0.0`, compiles at release
17, ships no native code, and the whole reactor stays buildable on JDK 17.

## Target layout

```
pom.xml                        org.gbif:text-tree-parent:2.0.0   (packaging pom)
├── text-tree/                 org.gbif:text-tree:2.0.0          release 17, 0 runtime deps
│     org.gbif.txtree
│       Tree, TreeNode, SimpleTreeNode, TreeLine
│       TreeNodeData      (new, public record)
│       TreeNodeFactory   (new, public functional interface)
└── text-tree-parsed/          org.gbif:text-tree-parsed:2.0.0   release 17
      org.gbif.txtree.parsed
        ParsedTree, ParsedTreeNode
      deps: text-tree, name-parser-api:5.0.0
```

A **new package** `org.gbif.txtree.parsed` rather than reusing `org.gbif.txtree` across two jars:
a split package works on the classpath but is an error on the module path and blocks `jlink`.
Cost is three import lines in one repo.

## API changes

### Core — added

```java
public record TreeNodeData(long id, String name, String rank, boolean extinct, boolean basionym,
                           boolean homotypic, boolean provisional,
                           Map<String,String[]> infos, String comment) {}

@FunctionalInterface
public interface TreeNodeFactory<T extends TreeNode<T>> { T create(TreeNodeData data, T parent); }

public static <T extends TreeNode<T>> Tree<T> Tree.parse(Reader, Consumer<TreeLine>, TreeNodeFactory<T>)
public static Tree<SimpleTreeNode> Tree.simple(Reader, Consumer<TreeLine>)
```

`TreeNode` widens from package-private to **public** — required so `ParsedTreeNode` can extend it
from another package. Its fields were already reachable through the public `SimpleTreeNode`.

The private `parse(Reader, Consumer<TreeLine>, BiFunction<Long,Matcher,T>)` becomes public but
takes `TreeNodeFactory` instead: the `BiFunction<Long,Matcher,T>` form would leak regex group
indices into the public API. A record parameter object is preferred over a 9-argument functional
interface so the format can gain fields without breaking implementors.

The factory also receives the node's `parent` (null at root level) so a node's interpretation can
depend on its ancestors — which D7 needs for `CODE` inheritance, and which keeps the factory
stateless and reusable. `Tree.parse` therefore trims its parent stack *before* calling the factory
rather than after, so a badly indented line now fails before the factory runs instead of after.

### Core — removed (moved to `text-tree-parsed`)

`Tree.parsed(...)` (4 overloads), `Tree.parsedNode`, `Tree.NAME_PARSER`, `Tree.LOG`,
`org.gbif.txtree.ParsedTreeNode`.

### Parsed module

```java
public final class ParsedTree {
  public static Tree<ParsedTreeNode> parse(InputStream, NameParser);
  public static Tree<ParsedTreeNode> parse(InputStream, NameParser, Consumer<TreeLine>);
  public static Tree<ParsedTreeNode> parse(Reader, NameParser);
  public static Tree<ParsedTreeNode> parse(Reader, NameParser, Consumer<TreeLine>);
  public static TreeNodeFactory<ParsedTreeNode> factory(NameParser);
}

public class ParsedTreeNode extends TreeNode<ParsedTreeNode> {
  public final ParseResult result;    // never null — the full three way result
  public final ParsedName parsedName; // null only for Unparsable results
  public final NomCode code;          // this line's CODE, else inherited, else null
}
```

`parsedName` is retained as a field so `coldp-generator`'s `n.parsedName.hasAuthorship()` keeps
working. It is populated from `Informal.toParsedName()` for informal results, preserving 4.x
behaviour where `NameParserImpl` returned a `type=INFORMAL` `ParsedName` rather than throwing.
As in 1.7.x, the rank given in the tree is written back onto the `ParsedName` so it wins over
whatever the parser inferred.

`TreeNode.rank` is now taken from the **line's** rank, not from the `ParsedName`. In 1.7.x an
unparsable name silently dropped its `[species]` marker because `rankOf(pn)` returned null when
`pn` was null.

## D7 — the nomenclatural code

`CODE` is a documented info key in the TextTree publishing guide
(`coldp/docs/publishing-guide-txtree.md:31` — "CODE: nomenclatural code of the name,
`CODE=zoology`"), and the CoL backend already interprets it: `TxtTreeInterpreter:34` reads it with
the comment *"CODE is inherited from above"*, falling back to the parent's, then does code-scoped
rank parsing at line 39. text-tree matches that.

`ParsedTree` resolves each node's code as **its own `CODE` info, else the one inherited from its
parent, else null**, exposes it as `ParsedTreeNode.code`, and — new in 2.0.0 — passes it to
`NameParser.parse(name, authorship, rank, code)`. 1.7.x always passed null there, losing parse
quality the parser could have had for free.

An unrecognised `CODE` value is ignored and the inherited code stands, matching the backend, which
records it as a data issue rather than failing the import.

### Mapping the CODE string

`name-parser-api` has no string→`NomCode` parser; the CoL vocabulary is a 47-entry CSV inside the
backend's `parser` module. text-tree ships a small map instead, built from the enum plus the
spellings the guide itself uses:

- every `NomCode.name()`, lower-cased — `botanical`, `zoological`, …
- every `NomCode.getAcronym()`, lower-cased — `icn`, `iczn`, `icnp`, `icncp`, `icvcn`
- common words — `botany`/`bot`/`plant`/`plants`, `zoology`/`zoo`/`animal`/`animals`,
  `bacteria`/`bact`/`prokaryotes`, `virus`/`viruses`, `cultivars`/`cultivated plants`,
  `phyto`/`phytosociology`, `phylo`/`phylocode`/`phylogenetic`

`PHYTO` and `PHYLO` both return `"ICPN"` from `getAcronym()`. Any acronym claimed by more than one
code is **dropped** rather than resolved to whichever the map happened to hit last — the same
refusal-to-guess that governs ambiguous ranks below. The collision is detected by counting
acronyms at map-build time, not hardcoded, so the entry reappears by itself if the api ever
disambiguates them.

## Rank resolution

`Rank.DIVISION` was removed in api 5.0.0 and replaced by `DIVISION_BOTANY` / `DIVISION_ZOOLOGY`,
completing a split that `SECTION`, `SUBSECTION`, `SUPERSECTION`, `SERIES`, `SUBSERIES` and
`SUPERSERIES` already had in 4.0.0. Bare forms of those six already threw from `Rank.valueOf` in
1.7.x and nobody reported it.

`ParsedTree.rank(value, line, code)` resolves in three steps:

1. **`Rank.valueOf` succeeds** — the rank was written unambiguously, including an explicitly
   code-qualified `[division zoology]`. Taken verbatim. Note this deliberately does *not* run
   `RankUtils.bestCodeCompliantRank`, which would silently rewrite an explicit `[division zoology]`
   to `DIVISION_BOTANY` under a `CODE=botany` ancestor. An explicit rank is the author's word.
2. **`<RANK>_BOTANY` exists** — the rank was written in the bare ambiguous form. If a code is in
   scope, `RankUtils.bestCodeCompliantRank` picks the right sibling; if none is, it throws with a
   message naming the code option and both explicit spellings.
3. **Neither** — throws, naming the rank and the line.

Note `bestCodeCompliantRank(rank, null)` returns `rank` unchanged, so the null-code case must be
rejected explicitly or step 2 would silently resolve every bare `[division]` to botany.

A bare `[division]` under `CODE=botany` therefore resolves to `DIVISION_BOTANY` and re-prints as
`[division_botany]`. That the text changes on a round trip is intended: the disambiguation is
information the tree did not previously carry.

## Defect fixed in this release

`Tree.isBlank` never returns `true` for an all-whitespace string — the loop falls through to
`return false` instead of `return true`. `Tree.verify` used `StringUtils.isBlank` (correct) while
`Tree.parse` used the broken one, so the two disagree:

```
$ printf 'Chordata [phylum]\n  Mammalia [class]\n   \n  Aves [class]\n' > ws.txtree
verify -> valid=true
simple -> IllegalArgumentException: Failed to parse Tree on line 3:
```

This matters in production: the CoL backend validates uploads with `Tree.verify`
(`ValidatorResource`) and then imports them with `Tree.simple` (`TxtTreeInserter`), so a file with
a whitespace-only line passes validation and then fails the import.

## Testing approach

`text-tree-parsed`'s unit tests use a hand written fake `NameParser` in test sources, not the Rust
binding. Two reasons: it keeps the whole reactor buildable and testable on JDK 17 (the Rust binding
needs 22+), and text-tree's job is mapping `ParseResult` → `ParsedTreeNode`, so a fake that returns
each of the three variants on demand tests those branches deterministically, which a real parser
makes harder. Wiring against the real `NameParserRust` is documented in the README instead.

*(Verified out of band during evaluation: `name-parser-rust:0.1.0` on JDK 25 / osx-aarch_64 parses
`Abies alba Mill.` → `Parsed`, `Rhizobium sp. RMCC TR1811` → `Informal`,
`Abies alba x Pinus picea` → `Unparsable/FORMULA`, extracting the cdylib from the classifier jar,
warning-only without `--enable-native-access=ALL-UNNAMED`.)*

## Out of scope

- The `vscode/` and `sublime/` syntax highlighting packages.
- The rank name round-trip quirk: `[cultivar group]` re-prints as `[cultivar_group]` from a parsed
  tree, because the rank is rendered as `Rank.name().toLowerCase()`. Pre-existing; both spellings
  are accepted on input. Left alone to keep this release focused.
